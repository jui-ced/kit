# 기술적 선택과 구현 설명

이 문서의 질문 대상은 **Probe 내부 메신저의 업무 담당자·실무자 에이전트**입니다. 외부 사람에게 연락하거나 문제·코드·작업물을 전달하지 않습니다.

사전 준비용 빈 양식이다. 실제 과제의 지정 기록 파일이 있으면 그 양식을 우선하고, 없으면 이 파일을 과제 작업 공간에 복사한다. 실제 시험 자료·답변·결과를 공개 kit에 기록하거나 Push하지 않는다. 특정 분야나 알고리즘을 전제로 하지 않는 범용 양식이며, 빈 항목은 실제 선택·구현·측정 기록이 아니다.

이 파일은 구현을 이해하기 위한 일반 Markdown 문서이며 설치형 Skill이 아니다. 업무 판단·실무자 에이전트 소통·전체 진행 이력은 [decisions.md](decisions.md)에, 기술적 선택의 상세 설명은 이 파일에 작성한다. 실제 구현 중 근거를 쌓고, 구현 완료 후 후속 설명 단계가 시작되기 전에 읽기 쉬운 설명으로 정리한다. 실제 후속 문항을 예측하거나 답변을 지어내지 않는다. 후속 단계의 AI·자료 열람 가능 여부는 운영 안내를 따른다.

## 먼저 읽는 구현 요약

구현 완료 후 아래를 실제 코드와 검증 기록에 근거해 채운다. 전문 용어는 처음 등장할 때 쉬운 뜻을 붙인다. 설명 순서는 '무엇을 만들었는가 → 어떻게 동작하는가 → 왜 이 방법인가 → 어떻게 확인했는가 → 한계는 무엇인가'로 한다.

- 해결한 문제와 핵심 기능을 3~5문장으로 설명:
- 전체 입력 → 처리 → 출력 흐름:
- 핵심 구성요소와 각각의 역할:
- 중요한 기술 선택과 선택 이유:
- 실제 확인한 성능·정확성과 근거:
- 미구현·미검증 범위와 한계:

| 기술 ID | 기능·선택 | 관련 업무 결정 ID | 아래 상세 설명 위치 | 실제 코드·검증 근거 |
|---|---|---|---|---|

## 기록하는 순서

1. 문제·목표·제약을 정리하고 애매한 업무 조건을 실무자 에이전트에게 묻는다.
2. 적용 가능한 알고리즘 2~3개와 간단한 비교 기준안을 설명한다. 원리·구성·정확성·시간·메모리·구현 비용을 비교한다.
3. 사용자에게 우선할 기준, 알고리즘, 주요 설정의 선택과 이유를 묻는다. 답변 전에는 **결정 대기**로 두고 본 구현에 채택하지 않는다.
4. 선택에 실측이 필요하면 먼저 비교 실험의 범위·시간 예산을 사용자에게 제안해 확인받는다. 비교 실험은 알고리즘 채택과 구분한다. 결과를 제시한 뒤 최종 선택을 다시 묻는다.
5. 구현 전에는 선택 이유를, 구현 후에는 실제 구성·변경 이유·측정 결과를 추가한다. 이전 기록을 지워 사후적으로 이유를 맞추지 않는다.
6. 새 근거로 알고리즘·목표·가중치·핵심 설정을 바꿔야 하면 비교와 사용자 결정을 다시 기록한다. 새 근거 없이 이미 확정한 선택을 반복해서 묻지 않는다.

## 결정별 기록 양식

아래 A~G를 기술 결정마다 복제한다. 관련 질문과 일반 작업 이력은 [decisions.md](decisions.md)의 ID로 연결한다. 업무 목표·가중치의 결정 과정은 decisions.md를 참조하고, 이 문서에는 그 조건이 기술 선택에 미친 영향을 설명한다. 기술 후보 비교와 해당 후보에 대한 사용자 선택의 상세 기록은 이 문서를 기준으로 한다.

### B. 후보 알고리즘의 지식과 구성

후보마다 다음을 작성한다. 라이브러리 이름만으로 알고리즘 설명을 대신하지 않는다. 모델링 방식, 탐색 알고리즘, 이를 실행하는 솔버·라이브러리를 구분한다.

- 후보 이름 / 모델링 방식 / 알고리즘 / 솔버·라이브러리·버전:
- 기본 원리: 비전공자도 이해할 수 있는 설명 3~5문장:
- 기본 구성: 입력·상태 표현 → 초기화 → 선택/탐색/갱신 → 제약 확인 → 종료 → 출력:
- 핵심 자료구조, 수식 또는 짧은 의사코드:
- 주요 설정(초기해, 이웃 탐색, 반복 수, 시간 한도, 난수 시드 등)과 영향:
- 정확해/근사해/휴리스틱 여부, 최적성 또는 근사 보장의 조건:
- 시간·공간 복잡도와 변수 정의, 최악/평균/기대 중 어느 분석인지:
- 현재 데이터 규모·제약에 맞는 이유 / 맞지 않는 조건:
- 실패·편향·재현성·해가 없는 경우의 처리:
- 설명의 근거 문서·논문·URL·버전·관련 부분:

확인되지 않은 복잡도는 미확인으로 남긴다. 라이브러리 전체에 단순한 Big-O를 임의로 붙이지 않고, 직접 분석 가능한 단계와 솔버의 데이터 의존적 탐색을 구분한다.

### D. 효율 비교 실험

“얼마나 효율적인가”를 실행 속도, 메모리, 해 품질로 나눠 기록한다. 측정하지 않은 수치를 만들지 않는다. 이론상 유리함이 실제로 몇 배 빠르다는 뜻은 아니다.

- 비교 대상·기준 알고리즘 / 동일한 목적함수·제약·가중치:
- 데이터 버전·규모·선정 이유 / 소규모 정답 검증 데이터:
- 실행 환경·버전 / 동일 시간 예산·종료 조건 / 난수 시드·반복 횟수:
- 시간에 포함한 범위(전처리·모델 생성·탐색·검증), 메모리 측정 방법:
- 해의 유효성을 별도 확인한 방법:

| 후보·설정 | 데이터·시드 | 시간(초) | 최대 메모리·단위 | 목적값·방향 | 업무 지표 | 제약 위반 수 | 종료 상태·최적성 근거 | 로그 경로 |
|---|---|---|---|---|---|---|---|---|

- 반복 측정 요약(중앙값·범위 등)과 변동:
- 속도 배율 = 기준 시간 / 후보 시간. 시간이 0이거나 측정 해상도 이하이면 계산하지 않는다.
- 시간 감소율 = (기준 시간 - 후보 시간) / 기준 시간 × 100. 양수인 기준 시간과 동일 측정 범위가 필요하다.
- 해 품질은 원시 목적값·차이·최적값/하한 대비 격차를 구분한다. 격차 계산식·분모·최대화/최소화 방향을 명시하며, 비교 기준이 0이거나 의미 없는 경우 비율 대신 원시 차이를 쓴다.
- 최적해를 모르면 '최적 대비 개선'이라고 쓰지 않는다. 제약을 위반한 결과를 유효한 해와 같은 품질로 비교하지 않는다. 시간 종료·실행 오류·해 미발견을 별도 표시한다.
- 이번 실험에서의 결론 / 다른 규모에 일반화할 수 없는 한계:

## 문제 유형에 맞춰 사용하는 방법 (범용 적용)

데이터 처리·검색·추천·예측·최적화·업무 자동화·웹 서비스 등 실제 문제에 맞춰 사용한다. 특정 알고리즘을 기본 정답으로 정하지 않는다.

- 최적화 문제가 아니면 목적함수·결정 변수 대신 처리 목표·입출력 규칙·성공 기준을 적는다. 최적성·근사 보장·최적값 대비 격차처럼 해당하지 않는 항목은 '해당 없음'과 이유를 남긴다.
- 알고리즘 외에 처리 방식·자료구조·시스템 구성이 핵심 선택이면 같은 양식으로 원리·구성·대안·선택 이유를 기록한다. 불필요하게 복잡한 알고리즘을 도입하지 않는다.
- 후보는 같은 요구사항을 해결할 수 있는 방법 중에서 선정한다. 비교 가능한 대안이 없으면 억지로 후보를 채우지 말고 제약과 검토한 대안을 설명해 사용자에게 확인한다.
- 품질 지표는 처리 정확성·검색 적합성·예측 오차·제약 충족·응답 시간 등에서 과제에 필요한 것을 골라 정의와 단위를 적는다. 어느 지표를 우선할지는 사용자에게 묻는다.
- 특정 데이터·업무에서의 실측 결과를 다른 문제에서도 동일하게 성립하는 효율로 일반화하지 않는다.

## 범용 질문·기록 예시

대괄호를 실제 관찰과 비교 근거로 채운다. 확인하지 않은 내용은 '미확인', 실행하지 않은 비교는 '미측정'으로 남긴다.

> 현재 문제는 [입력]으로부터 [출력]을 만드는 것이고, 반드시 지킬 조건은 [제약]입니다. 후보 A는 [원리와 처리 단계], 후보 B는 [원리와 처리 단계]로 동작합니다. A는 [장점·비용], B는 [장점·비용]이 있습니다. 이론적으로 확인한 내용은 [근거], 실제 측정한 내용은 [결과 또는 미측정]입니다. 저는 [이유]로 [후보]를 추천합니다. 이번 과제에서는 [품질·시간·자원·설명 가능성 등] 중 무엇을 우선하고 어느 방식을 선택하시겠어요? 선택 이유도 알려주세요.

사용자 선택 후 기록:

- 선택한 방법과 사용자가 중요하게 본 기준:
- 핵심 원리와 실제 구현 단계·코드 위치:
- 다른 방법보다 현재 요구사항에 적합한 이유와 근거:
- 예상과 실제 구현·측정 결과의 차이:
- 남은 한계와 재판단이 필요한 조건:

업무 의미가 애매하면 실무자 에이전트에게 먼저 확인할 질문을 제시하고, 답변을 반영한 비교를 사용자에게 보여준다. 구현 후 방향 변경이 필요해도 사용자 결정 절차를 유지한다.
