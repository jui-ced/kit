# 실무자 에이전트에게 물을 질문과 개발자가 판단할 사항

이 문서의 질문 대상은 **Probe 내부 메신저의 업무 담당자·실무자 에이전트**입니다. 외부 사람에게 연락하거나 문제·코드·작업물을 전달하지 않습니다.

질문을 많이 준비하되 한 번에 모두 묻지 않는다. 자료로 이미 확인한 내용은 생략하고, 결정에 큰 영향을 주는 3~5개부터 대화한다. 아래 예시의 대괄호는 실제 관찰로 바꾸며, 예시 자체를 사실로 기록하지 않는다. 허용된 시험 내 대화 채널을 사용하고 규정·제출 방식은 운영 측에 확인한다.

## 1. 문제를 처음 이해할 때

| 목적 | 실무자 에이전트에게 할 구체적 질문 | 답변 후 사용자가 판단할 것 |
|---|---|---|
| 실제 사용자 | 이 결과를 누가, 어느 업무 단계에서 확인하고 어떤 행동을 하나요? 최근 사례 하나를 순서대로 설명해주실 수 있나요? | 핵심 사용자와 구현할 업무 흐름 |
| 현재 불편 | 현재 수작업에서 시간이 가장 오래 걸리거나 재작업이 많은 단계는 어디인가요? 대략 얼마나 자주 발생하나요? | 자동화할 단계와 우선순위 |
| 문제의 결과 | 이 문제가 해결되지 않으면 어떤 업무가 지연되거나 어떤 손실이 생기나요? | 속도·정확성·편의성 중 중요 기준 |
| 성공 기준 | 결과물이 유용하다고 판단할 때 실제로 확인하는 지표나 사례가 있나요? 현재 기준값과 허용 가능한 범위가 있나요? | 측정할 완료 기준과 검증 방식 |
| 고려하지 못한 부분 | 처음 이 업무를 맡은 사람이 자주 놓치는 조건은 무엇인가요? 정상 사례와 다르게 처리하는 사례도 알려주세요. | 추가 확인·예외 처리 범위 |

## 2. 데이터를 확인할 때

| 목적 | 실무자 에이전트에게 할 구체적 질문 | 답변 후 사용자가 판단할 것 |
|---|---|---|
| 행·필드 의미 | 한 행은 [설비/작업/측정] 중 무엇을 뜻하나요? [컬럼]의 단위와 기록 시점은 무엇인가요? | 집계 단위·그룹 기준 |
| 결측치 | [컬럼]에 빈 값이 있습니다. 미측정·해당 없음·입력 지연 중 어떤 경우인가요? 서로 구분할 수 있나요? | 제외·별도 표시·추가 확인 정책 |
| 중복 | 같은 [키]가 여러 행에 있습니다. 반복 측정인가요, 중복 저장인가요? 최신 행을 구분할 기준이 있나요? | 중복 유지·제거·선택 방식 |
| 이상값 | [범위 밖 값]은 실제 가능한 상황인가요, 기록 오류인가요? 확인할 다른 자료가 있나요? | 이상값 표시·분리·처리 기준 |
| 비교 가능성 | 기간·설비·제품별로 측정 방식이나 조건이 달라 직접 비교하면 안 되는 경우가 있나요? | 비교 대상과 결과 해석 범위 |
| 대표성 | 제공 자료에서 빠진 기간·상황이 있나요? 이 자료만으로 결론 내리기 어려운 것은 무엇인가요? | 결론의 강도와 한계 표시 |

## 3. MVP와 중요도를 정할 때

| 목적 | 실무자 에이전트에게 할 구체적 질문 | 답변 후 사용자가 판단할 것 |
|---|---|---|
| 기능별 효과 | [A 기능]과 [B 기능]은 각각 어떤 업무를 얼마나 줄이나요? 하나가 없어도 기존 방식으로 보완할 수 있나요? | 제한 시간 내 우선 구현 범위 |
| 오류 피해 | 실제 문제를 놓치는 경우와 정상 건을 잘못 경고하는 경우, 각각 어떤 후속 작업·피해가 생기나요? | 오류 유형별 중요도와 임계값 |
| 처리 시급성 | 결과는 즉시 필요한가요, 일별 확인으로 충분한가요? 늦어져도 되는 범위는 어느 정도인가요? | 실시간·일괄 처리와 성능 목표 |
| 설명 필요성 | 담당자가 결과를 믿고 행동하려면 어떤 근거나 원본 항목을 함께 봐야 하나요? | 근거 표시·상세 조회 범위 |

“무엇부터 개발할까요?”로 결정을 넘기기보다 효과·빈도·피해·대체 방법을 묻는다. 실무자 에이전트가 중요하다고 말한 이유를 확인하고, 그 정보로 참가자가 구현 우선순위를 정한다. 공식 요구사항은 먼저 충족한다.

## 4. 구현·검증 중 다시 물을 때

| 상황 | 실무자 에이전트에게 할 구체적 질문 | 답변 후 사용자가 판단할 것 |
|---|---|---|
| 새 예외 발견 | [조건]에서 기존 규칙을 적용하면 [결과]가 나옵니다. 실제 업무에서도 이렇게 처리하나요? 예외 기준이 있나요? | 규칙 수정 또는 예외 표시 |
| 자료와 답변 충돌 | README에는 [A], 앞선 설명에는 [B]가 있습니다. 적용 시점이나 대상이 다른가요? 확인할 근거가 있나요? | 운영 확인 필요 여부·구현 보류 범위 |
| 결과 검토 | [입력→결과]가 실제 업무 판단과 맞나요? 반대로 나와야 하는 구체적 사례가 있나요? | 반례 테스트와 처리 수정 |
| 사용성 확인 | 이 화면/출력으로 다음 업무를 할 수 있나요? 추가로 찾아봐야 하는 정보는 무엇인가요? | 필수 출력 보완 또는 후순위 처리 |
| 남은 위험 | 현재 [제약]이 남아 있습니다. 실제 사용에서 문제가 되는 상황과 빈도는 어느 정도인가요? | 남은 시간 내 수정·한계 명시 선택 |

## 중간에 애매한 부분을 발견했을 때 제시할 형식

핵심 기능 구현 전후·중간 결과 확인·오류 조사 중 새 모호점이 생기면 즉시 제시한다. 처음의 질문 목록이나 마지막 검토 시점까지 미루지 않는다.

- 관찰: [실제 파일·필드·결과에서 확인한 내용]
- 모호점·고려사항: [아직 확정할 수 없는 업무 의미 또는 빠뜨린 조건]
- 지금 확인할 이유: [잘못 가정했을 때 달라지는 결과·재작업]
- 실무자 에이전트에게 전달할 질문: “[구체적인 상황]에서는 [A/B/그 밖의 처리] 중 실제로 어떻게 처리하나요? 판단 근거와 예외도 알려주세요.”
- 답변의 영향: [바뀔 구현·테스트 또는 사용자에게 다시 물을 선택]
- 대기할 작업 / 계속할 작업: [해당 규칙 구현] / [영향받지 않는 검사·구현]
- 답변 후: [해결 여부·후속 질문·사용자 판단·계획 갱신]

예시: “같은 설비·시각인데 측정값이 다른 행이 있습니다. 이를 하나로 합치면 결과가 달라집니다. 재측정값인지 서로 다른 측정 항목인지, 유효한 기록을 구분하는 기준이 있는지 확인해주실 수 있나요?” 답변 전에는 중복 제거를 보류하고 발생 건수와 다른 컬럼 검사는 진행한다.

## 답변을 들은 뒤 이어갈 질문

- “중요하다” → 어떤 상황에서, 얼마나 자주, 틀리면 어떤 피해가 생기나요?
- “보통 이렇게 한다” → 다르게 처리하는 예외와 그 판단 기준은 무엇인가요?
- “정확해야 한다” → 어떤 오류가 특히 문제이며 허용 범위나 비교 기준이 있나요?
- “잘 모르겠다” → 확인 가능한 자료나 담당자가 있나요? 없다면 어떤 부분을 미확인으로 남겨야 하나요?

## 사용자에게 판단을 다시 묻는 예시

아래는 질문 형식 예시이며 실제 실무자 에이전트 답변이 아니다.

> 실무자 에이전트 답변에 따르면 [문제 누락의 피해]가 크지만, 경고가 많아지면 [검토 부담]이 생깁니다. A는 탐지 범위를 넓혀 누락을 줄이는 방향이고, B는 경고를 줄여 검토 부담을 낮추는 방향입니다. 제공 데이터로 확인한 근거는 [내용]이며 아직 [불확실성]이 남아 있습니다. 저는 [이유]로 A를 추천합니다. 이번 MVP에서는 어느 위험을 더 줄이는 데 가중치를 두시겠어요? 선택 이유도 알려주세요.

> [빈 값]의 의미는 아직 확인되지 않았습니다. A는 해당 행을 별도 표시하고 계산에서 제외하며, B는 추가 확인 전까지 집계 확정을 보류합니다. 각각 [영향]이 있습니다. 어떤 방식을 선택하시겠어요? 답변 전까지 원본 검사와 다른 필드 검증은 진행하겠습니다.

사용자 답변을 받은 뒤 templates/decisions.md에 근거·선택·이유를 남기고 templates/plan.md의 순서와 완료 기준을 수정한다. 실무자 에이전트 확인과 사용자 결정이 끝나지 않은 사항은 확정된 요구사항처럼 구현하지 않는다.
